# What the two 1.5B jobs do

Historical description: the user stopped k=0 and replaced the eight-GPU k256 job with the [twelve-GPU high-priority study](runs/deepseek15b-multinode-12gpu.md). The schedules below explain the earlier jobs.

Both studies start from the same pinned `deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B` weights, use the same cleaned DeepScaleR questions and grader, and target 1,000 optimizer updates. They are separate runs with separate optimizer states and output directories. Neither resumes the 13 updates from the stopped job `2145184`.

| Job | Purpose | Priority | Startup | Study |
| --- | --- | --- | --- | --- |
| `2145261` | On-policy baseline | Normal | Stage local files and run hardware/data integrity checks | Directly train 1,000 updates with k=0; no timing benchmark |
| `2145258` | Exact-staleness comparison | High | Stage files, check hardware, run two old-settings and two optimized-settings benchmark updates | If validation passes and optimized mean update time is lower, start a fresh 1,000-update k=256 study |

The baseline is assigned to node 7 with four training and three inference GPUs. This is an explicit exception for the seven working GPUs on that eight-GPU node. The k=256 job still requires four training plus four inference GPUs on a healthy node. GPU topology and the earlier thermal-throttling observation must be considered in timing comparisons. Scheduler RUNNING can describe staging or health checks before any optimizer update occurs.

## Common update

1. Select 64 questions and generate eight responses per question: 512 responses total. Each prompt is limited to 2,048 tokens and each response to 8,192 tokens.
2. Record generated token IDs, masks, behavior-policy log probabilities, policy version and response/question mappings. The grader assigns rewards from the final answer under the pinned grading policy.
3. Calculate each response's advantage by centering rewards within its eight-response question group. Pack the batch across four trainer GPUs, retaining all responses and their token context.
4. Compute the clipped GRPO objective using the probability ratio `exp(current_logprob - behavior_logprob)`, with clipping epsilon 0.2 and global response-token normalization. Apply one AdamW update to the complete batch, then synchronize the updated model to inference. There are no extra optimization epochs on the cohort.
5. Advance the policy version exactly once and log the update's provenance, rewards, lengths, loss/gradient diagnostics, token contribution fractions and timings. Zero-advantage or zero-direct-gradient tokens are logged, not removed. An update is not skipped merely because its immediate gradient contribution is zero.

Both configurations use LR 1e-6 with 30 optimizer updates of LR warmup, zero weight decay, no reference KL penalty, gradient-norm clipping at 1, seed 42, BF16 computation with FP32 optimizer/reduction, activation checkpointing enabled and compilation disabled. Disabling compilation refers to the learner; vLLM inference still performs its normal kernel compilation and CUDA-graph preparation during startup. Optimized execution uses 64 active sequences per inference GPU, dispatcher concurrency 256 and forward resharding disabled. Official PrimeRL/vLLM source is unchanged; the local adapter passes through their existing execution configuration.

## On-policy k=0

At zero-based learner version t, generate the training cohort using policy t, train on it, then synchronize policy t+1 before generating again. Behavior version equals learner version before every update, so logged age is always zero. There is one generated cohort per update and no deferred rollout queue. This is ordinary on-policy GRPO, with the existing 30-update LR warmup still enabled.

## Exact k=256

The four diagnostic updates run separately and are discarded as training progress. They do not establish age-256 behavior: they exercise the beginning of the bootstrap. After they pass, the full study starts again from the original model and optimizer initialization.

The full study has three phases, using one-based update numbers:

| Updates | Data consumed for training | Other generation work |
| --- | --- | --- |
| 1–256 | A fresh on-policy cohort; logged age zero | Generate another cohort with the same current policy and retain it for use 256 updates later |
| 257–744 | The cohort generated by policy t−256, where t is the learner version before the update | Generate a new deferred cohort with policy t while the learner trains |
| 745–1,000 | Remaining queued cohorts, still exactly age 256 | Stop generating new cohorts; drain the queue |

For example, update 257 starts with learner version 256 and consumes the deferred cohort generated with policy version 0. Update 258 consumes version-1 data at learner version 257. Both have age 256. The first 256 bootstrap updates must be distinguished from the 744 measured exact-age updates in research analysis.

This implementation delays rollout data. It does not generate new responses by repeatedly loading a policy checkpoint from 256 updates ago. Each queued cohort retains its original responses, rewards, masks and behavior log probabilities; it is not re-generated or silently refreshed before training. Queued data and progress are part of recovery checkpoints.

## Storage, tracking and completion

Source, Python runtime, model/tokenizer/data, caches and active outputs are staged on node-local storage and verified. Full recovery checkpoints are written every 100 optimizer updates; background copies to NFS are checksum-verified before publication. Metrics and TensorBoard data also have the configured XFS copy. Intermediate task evaluations are disabled; there is no Runboard process. Saved checkpoints can be evaluated offline later.

The jobs stop at 1,000 updates. Automatic Slurm requeue is disabled. Errors and failed health checks exit with diagnostics rather than silently changing model, loss or starting over. The k=256 launcher additionally refuses to start its full study if its bounded timing/readiness comparison fails. A normal-priority allocation can be preempted by higher-priority scheduling; recovery uses a complete compatible checkpoint and must preserve the experiment's progress and policy-version accounting.
