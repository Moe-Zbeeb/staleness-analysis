# Review guide

The entry point is `deepseek-study`. Each invocation uses one explicit lag; the package does not schedule sweeps or start training during setup.

For the scientific review, read the [staleness research audit](staleness-research-audit.md). It identifies which settings affect age versus tolerance, traces the effective loss and logging semantics, and distinguishes implemented controls from missing evaluation and diagnostic work.

## Code map

| Concern | Files | Review question |
| --- | --- | --- |
| Public interface and scientific settings | `cli.py`, `config.py`, `recipe.py`, `runtime/build.py` | Are every run's settings explicit and validated before launch? |
| Exact-k scheduling | `rollouts/queue.py` | Is every consumed rollout exactly k optimizer updates old after bootstrap? |
| PrimeRL integration | `rollouts/controller.py`, `runtime/launcher.py` | Are inference weights frozen for a complete cohort and process failures fatal? |
| GRPO objective | `learning/advantages.py`, `learning/loss.py` | Do advantages, original behavior probabilities, masks and global token normalization agree? |
| Model and data provenance | `dataset/assets.py`, `dataset/prepare.py`, `manifests/`, `assets/train-manifest.json` | Are native tokenization, input identities and exclusions reproducible? |
| Grading | `dataset/rewards.py`, `dataset/grading.py`, `dataset/worker.py`, `deepseek_deepscaler/` | Are mathematical correctness and infrastructure failures distinguished? |
| Recovery | `runtime/checkpoints.py`, `runtime/trainer.py`, `runtime/trainer_state.py` | Is a checkpoint usable only after all required state is committed? |
| Reproducibility and auditing | `runtime/identity.py`, `rollouts/audit.py` | Do source snapshots and logs bind the actual run and consumed cohorts? |
| Installation and deployment | `scripts/bootstrap.py`, `scripts/package.py`, `scripts/cluster_prepare.py`, `scripts/gpu_health.py` | Can dependencies, assets and hardware be checked without launching the study? |
| Bounded GPU readiness | `scripts/readiness.py`, `scripts/weight_transfer_probe.py` | Do real generation, GRPO updates, metric export and checkpoint recovery pass without launching the production run? |

Python module paths in this table are relative to `src/deepseek_study/`, except the taskset package at `src/deepseek_deepscaler/`. `scripts/`, `manifests/` and `assets/` are relative to the experiment root. Tests mirror these concerns under `tests/`; `configs/` holds the schema and an intentionally incomplete template whose lag must be chosen. The [architecture](architecture.md) includes the full tree; the [integration guide](upstream-integration.md) identifies every library customization.

## Algorithm contract

`theta_t` denotes the model after t completed optimizer updates. The update producing `theta_(t+1)` consumes data generated by `theta_(t-k)` once t is at least k. Every complete cohort produces one optimizer update, even when every advantage is zero. Packed microbatches do not advance the policy-version counter independently.

For k=2, the first four updates are:

| Current model | Consumed rollout policy | Age | Phase |
| --- | --- | --- | --- |
| theta_0 | theta_0 | 0 | Bootstrap |
| theta_1 | theta_1 | 0 | Bootstrap |
| theta_2 | theta_0 | 2 | Exact-k |
| theta_3 | theta_1 | 2 | Exact-k |

Bootstrap responses and deferred responses are separate samples. Prompts are assigned by intended consumption update so changing k preserves the assigned question stream. Generation stops before the end of training so the queue drains without unused cohorts. A checkpoint binds the pending queue to the original total horizon.

The initial k updates are explicitly on-policy, not exact-k. The default 1,000-update budget includes them. Delaying responses changes which model generated them; it does not require loading a series of historical inference checkpoints.

## Validation and limits

The current package passed 128 local CPU tests (one CUDA case skipped) and all 129 tests in full-node cluster job `2144960`. The added CUDA case checks CPU rollout metadata against GPU model outputs and actual GRPO gradients. Earlier CPU-only job `2144956` passed the preceding 128-test suite. The suite covers scheduling across multiple k values and horizons, queue recovery, duplicate/version rejection, official packing and transport serialization, GRPO gradients and masking, grading timeouts, data contracts, tokenizer parity, source snapshots, checkpoint integrity and configuration resolution. Additional checks cover globally weighted paper diagnostics, raw token capture, XFS mirroring and offline evaluation provenance. Runboard checks cover file/HTTP delivery, metric clocks, outage spooling, observer shutdown and failure isolation. Job `2144956` also verified three exact rows from the live backend, including all 281 diagnostic scalars; see the [integration guide](runboard.md).

Cluster preparation verified all 11 pinned model files and five native-tokenizer probes. GPU diagnostic `2144920` passed on eight A100 80GB GPUs: NCCL all-reduce returned 36 on every rank, BF16 and Flash Attention backward passed, and vLLM RMSNorm matched its Torch reference. The diagnostic does not load or train the 14B model. See [validation evidence](../diagnostics/cluster-validation.json) and [cluster operations](cluster.md).

Those CPU and component checks alone do not establish end-to-end readiness. The later [bounded GPU test](readiness-test.md) records live model execution and recovery validation. The production exact-256 run has not been launched; its 512-response batch, full queue memory and long-run stability remain separate validation limits.

Future inference after resume is not bitwise reproducible because full vLLM RNG state is not restored. The GPU readiness test also observed small backward/optimizer differences despite identical saved forward log probabilities; strict deterministic GPU training is not configured. Large trainer checkpoint shards are checked by size, while metadata and smaller state files are hashed. Cross-layout resume and automatic benchmark evaluation are not implemented.

The integration imports pinned internal PrimeRL APIs. Upgrade the dependency pin only after reviewing those interfaces and rerunning the contract suite. The official checkout is never patched by this package.

The [bounded readiness protocol](readiness-test.md) records the real-model diagnostic scope and integration issues found on the eight-A100-80GB PCIe node.
