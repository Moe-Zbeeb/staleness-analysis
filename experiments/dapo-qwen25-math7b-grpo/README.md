# Qwen2.5-Math-7B DAPO GRPO

This experiment runs full-parameter GRPO with Prime RL v0.9.0 on Qwen2.5-Math-7B. It uses four trainer GPUs and two independent vLLM data-parallel replicas on one six-GPU node.

Prime RL uses FSDP2, so this replaces the proposed DeepSpeed ZeRO-3 implementation while preserving full-parameter training. Qwen2.5 uses the Hugging Face model implementation and FlashAttention 2 because Prime's custom-model and automatic Hopper attention paths do not support this architecture in v0.9.0.

The training set is the `all` configuration of DAPO-Math-17k-Processed. It contains 17,398 source rows. The repository's 34,796 total counts `all` plus the `en` and `cn` views, which repeat the same bilingual collection. The pinned preparation retains 17,005 rows after removing 213 canonical duplicate extras, all five conflicting duplicate groups, 112 automatically matched held-out overlaps, 55 manually audited held-out variants, and 8 prompts over the 1,024-token budget. It shuffles with seed 42 and records source revisions, exact hashes, row counts, conflict evidence, contamination evidence, and tokenizer-derived lengths in `data/manifest.json`.

The reward is deterministic terminal-answer mathematical equivalence with no LLM judge and no separate format reward. It accepts an exact final-answer line or a boxed answer at the absolute end of the response, including standard inline and display-math closers, while rejecting corrections or other content after the answer. A smoke trace exposed a false negative for a correct answer ending in `\(\boxed{9}\).`; the anchored closer handling now has positive and adversarial regressions. The custom Prime loss implements PPO ratio clipping at epsilon 0.2 and records mean, minimum, and maximum importance ratios plus clip fraction. Prime's built-in all-zero, all-one, and mixed-group metrics remain available in `metrics.jsonl`.

Training uses a 4,096-token total context with at most 3,072 completion tokens. The model's native context is 4,096, so a 4,096-token completion would not fit after the prompt. Production checkpoints are written every 25 steps, the last four are retained, and every 100-step checkpoint is retained permanently. Prime v0.9 writes the complete model, optimizer, scheduler, and progress state synchronously and has no asynchronous checkpoint mode. The two-step smoke therefore uses an interval of two, which suppresses the redundant step-one save while retaining the mandatory final step-two save. The persistent checkpoint target is on NFS and is exposed through `/mnt/xfs/home/mohamadzbib/projects/models/qwen25-math7b-grpo-seed42` as required by the workspace model layout. The projected retained production set is about 1.11 TB, and the launch preflight measured 22.3 TB available on the target filesystem.

The model's original tokenizer declares `<|endoftext|>` as EOS even though its chat template closes assistant turns with `<|im_end|>`. Preparation saves an otherwise identical tokenizer overlay with `<|im_end|>` as EOS so Prime's generic renderer stops completed turns instead of consuming the remaining token budget.

MATH-500, AIME 2024, AIME 2025, and AMC 2023 run greedily at startup and every 100 steps. Minerva Math and OlympiadBench run at startup and the final step. AIME 2024, 2025, and 2026 also run with eight temperature-0.6 samples at startup and the final step for pass@k estimates.

Prime's JSONL monitor is the durable metric source. A separate pinned Opik 2.2.61 sidecar uploads selected scalar rows, persists its offset outside Prime's run directory, and must complete an authenticated startup trace and feedback-score upload before training begins. Each trace carries a Slurm attempt identifier so abandoned and retrained steps remain distinguishable after a requeue. If telemetry fails, training fails closed. The API key is provisioned in a mode-0600 private credential file outside this directory and is not included in Slurm exports or logs.

The launch sequence is a relocatable Opik runtime build, a CPU data and configuration job, a same-topology six-GPU health and two-step end-to-end smoke job, then the 1,000-step production job. `deep-h-1` failed the CUDA health gate on all six allocated H100s before model load, so the active fallback uses six 80 GB A100s with four for FSDP2 training and two for vLLM data parallelism. Prime assigns the first two visible devices to inference. When Slurm allocates physical GPUs zero through five on `deep-chungus-11`, the launch order is changed to `4,5,0,1,2,3`, which keeps the two vLLM replicas on GPUs four and five and the four-way trainer on the better-connected zero-through-three group. Other scheduler allocations retain their original order. The first A100 smoke exposed an NCCL failure when Prime disabled both peer-to-peer and shared-memory transports; the replacement keeps PCIe peer-to-peer disabled but enables NCCL shared memory. A later smoke exposed verifier runtime startup blocking on the shared filesystem, so Prime now gives only the orchestrator and verifier subprocesses a job-local `HOME` and `UV_CACHE_DIR`. Probe job 2140450 proved that both generated verifier scripts and their Python environment resolve under node-local temporary storage. The production allocation uses an unlimited Slurm time limit (`--time=0`), verified by `TimeLimit=UNLIMITED`. The earlier eight-hour limit was an explicit job setting, not a cluster maximum. The batch wrapper uses `exec bash` so the training script receives batch-shell signals directly; the scheduled time-limit warning has been removed. Requeue remains enabled for scheduler interruptions, and the script resumes only from the newest step complete in both trainer and orchestrator state. Manifest-bound run, training-finished, and telemetry-complete markers prevent stale data or scripts from being silently accepted. Incomplete checkpoint directories and pre-checkpoint interrupted runs are moved to a recoverable archive rather than trusted or deleted.
