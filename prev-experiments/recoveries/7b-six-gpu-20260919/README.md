# Six-GPU continuation of 7B staleness caps 6 and 8

The user requested normal-priority scheduling on any compatible node with six available GPUs. Each job requests six GPUs on one node and uses four for training plus two inference replicas. Eligible placement covers the 80GB A100 node class (deep-chungus-7 through 11) and H100 nodes (deep-h-1 through 3). Slurm excludes unavailable nodes; the allocation probe independently requires six A100/H100 devices with at least 75 GiB each, correct allocated UUIDs, BF16 backward and an NCCL sum derived from world size. Older 40GB A100 and V100/2080Ti nodes are excluded from this continuation profile.

The cap-6 run resumes its paired step-125 checkpoint; cap-8 resumes step 100. Trainer world size stays four, preserving the existing distributed model and optimizer state. The overlay changes allocation from eight to six GPUs and inference data parallelism from four to two. Reward, training data, tokenizer, optimizer, batch/group sizes, staleness caps, decoding budgets and evaluation schedule remain unchanged. Changing hardware and inference throughput can affect asynchronous execution, so this is recorded as a new execution segment rather than a pure hardware-matched comparison.

Run and observer paths, Comet projects, model links and source/data manifests remain the original ones. Each copied launcher takes the original run lock, checks the unchanged source and smoke evidence, records the chosen checkpoint before launch and refuses to start from scratch. The original manifests and scripts are not rewritten. An existing paired step-1000 checkpoint without completion markers causes a stop for completion review rather than replaying earlier training.

`spec.json` binds the original source/data/guard hashes and the initial checkpoint evidence. `package-manifest.json` binds this recovery package. `guard.py` preserves original audit checks while resolving expected production settings with the overlay; it uses recorded resume evidence if the ordinary checkpoint-retention policy later removes a resume checkpoint. Its final report is saved under `validation/`.

`validate_plan.py` runs in a CPU Slurm allocation before submission to verify original smoke evidence, exact configuration differences, trainer/orchestrator checkpoint step metadata, optimizer presence and noncontiguous GPU mapping. Actual checkpoint tensor reload and GPU health remain startup checks in each training allocation.
